## Dependency notes

- Plan 001 fixes the typecheck baseline and defines the metadata needed by later plans. Do not build the dynamic MCP registry on top of an action model that still assumes every action is an arbitrary JavaScript string.
- Plan 002 is required before publishing generated action code as a broadly reusable tool. The current extension evaluates model-produced source with `new Function`; the executor must replace that trust boundary with a finite declarative operation set.
- Plan 003 keeps the generic `browserforge_run_read_action` compatibility path while adding stable business names such as `rdms_list_deployment_instances`.
- Plan 004 is the first product pilot and supplies real latency/token/success measurements before expanding tool count.
- Plan 005 is a design and verification spike. It does not enable order creation automatically.
- Plan 006 deliberately implements a lighter demo path from the Plan 005 findings: finite JSON, one confirmation, one click, no retry, and local-fixture verification. Production controls remain deferred.

## Findings considered and rejected

- Generate arbitrary or production-grade write tools immediately: still rejected. Plan 006 permits only a demo-specific finite write DSL with observable completion, one confirmation, one terminal click, and no automatic retry; it does not claim production safety.
- Replace the Chrome bridge with direct site APIs: rejected because the stated value is reuse of the current tab's login state and some sites expose no stable API; keep direct API adapters as a future opt-in optimization.
- Publish every generated action as an MCP tool: rejected because unstable or low-value tools increase tool-list context and make model selection worse. Only validated, explicitly published actions should be exposed.
- Add an MCP SDK dependency before the protocol surface is stable: rejected for now; the existing JSON-RPC stdio server is small. Reconsider after pagination, notifications, auth, or task support is required.
